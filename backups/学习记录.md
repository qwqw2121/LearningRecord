## 1. pipepline（11.02）

### **scheduled_flow.py :**

1. 定时生成昨日日报（调用**batch_daily_flow**批量生成） 
2. 每三小时采集新闻＋分析（直接调用task)
3. def **pipeline_lock**()**基于文件锁的进程间互斥机制**，用来确保同一时间只有一个流水线实例在运行。核心原理是利用操作系统提供的 `flock` 系统调用，通过一个锁文件来协调多个进程。 `flock` 是内核级锁，进程退出或崩溃时会自动释放

### **daily_news_flow.py**：

**抓取  →  正文提取  → 去重  →  LLM分析  →  Embedding  →  事件聚类  →  日报生成→ 质量检测（新增）** 

1. 抓取  **crawl_task**  

   **3天内 使用RSS（rss_crawler.py）:** 按日期从 YAML 配置的多路 RSS 源并发抓新闻，清洗后以 URL 为唯一键写入 SQLite（`status='raw'`），为后续的 LLM 处理准备原始数据；网络请求并发、数据库写入串行，单个源失败不影响整体

   - 准备数据库，初始化结构化数据库表
   - 处理 RSS 里带标签的标题和摘要
   - 标题去空格、转小写后做 MD5
   - 逐条 `INSERT`，靠 `news.url` 的 `UNIQUE` 约束做去

   **超过3天使用爬虫（backfill_crawler.py)：**按指定日期，从 arXiv 和 Hacker News 两个 API 精确回补历史新闻，复用 RSS 爬虫的清洗和入库逻辑，串行执行、带重试和限速，单源失败不影响整体，返回与 RSS 爬虫一致的统计结构。****

   - arXiv 按日期范围回补
   -  Hacker News 按时间+关键词+分数回补

2. 正文提取 **extraction_task**

   - 并发下载、按域名限速(同一域名两次请求至少间隔 `1.0` 秒)、trafilatura 优先、readability 兜底、失败重试有上限、最终降级放行。
   - 把 `raw` 状态的新闻 URL 并发下载、用 trafilatura/readability 抽正文，按域名限速、失败重试有上限并最终降级用摘要放行，把记录推进到 `extracted`，为后续 LLM 处理准备好正文内容。

3. 去重 **dedup_task**：<u>标题去重</u>

   - **title_hash 精确去重**：抓取阶段(crawl.py)已经给每条新闻算好了 title_hash(标题归一化后的md5)。  这里按 title_hash 分组,同一个hash只保留最早入库的一条(id最小),其余标记 is_duplicate=1。这一步抓的是"标题完全一样"的情况
   - 同日**标题模糊相似度聚类**：  抓"标题不完全一样,但明显讲的是同一件事"的情况,比如:  "OpenAI发布GPT-6" vs "OpenAI正式发布GPT-6大模型,性能大幅提升" 用 **difflib 算字符串相似度**,不需要调用任何模型,成本几乎为0。  按发布日期分桶比较,避免全库O(n^2)两两比较。
   - difflib 是 Python 标准库里的模块，用来做序列（尤其是字符串）的比较。**SequenceMatcher** 基于 **Ratcliff/Obershelp 算法**，核心是找两个序列的**最长匹配块**，然后递归地在剩余部分继续找匹配，最后用“匹配上的总字符数 × 2 / 两个字符串长度之和”得出比例。

4. LLM分析 **analysis_task**

   LLM_ANALYSE：输出json{{

   ​      "summary": "",

   ​      "category": "",

   ​      "keywords": [],

   ​      "importance": 1

   ​      }}

   select ('deduped', 'analyze_failed')

   它按源配额采样待分析新闻，用全局限流 + 指数退避重试并发调用 LLM，经 `_normalize` 校验清洗后批量写回数据库并推进到 `analyzed`

   ❓⁉新增：CATEGORIES = {"大模型发布", "融资并购", "政策监管", "研究论文", "产品发布", "行业观点", "其他"}**后续如何用到**

5. Embedding **embedding_task**

   *引擎 1：本地 BGE-M3 (懒加载)*

   *引擎 2：在线 API (懒加载)*  text-embedding-v4/text-embedding-v3

   把**标题、摘要、分类、关键词拼成一段文本**，对 `None` 和 `keywords` 的 JSON 字符串做了防御性处理，保证不返回空串。

   **⭐❗优化：**最初版本是“能跑通”的串行脚本：逐条提交、无重试上限、本地模型可能重复加载、向量库写入的线程安全没考虑。修改后的版本在**吞吐（并发+限流）、成本控制（失败上限）、稳定性（重试退避、主线程写库、批量提交、中断兜底）** 四个维度都有实质提升

6. 事件聚类  **clustering_task**

   **增量聚类**：不重跑全量，只处理新来的新闻，用向量近邻 + 时间窗口决定归属。

   之前：

   用**向量近邻 + 相似度阈值 + 3 天时间窗口，把新向量化的新闻增量归并到已有事件或新建事件**，事务内完成**关系与状态更新，幂等、单条失败不影响整体**，是“新闻 → 事件”聚合的关键一步。

   不再简单地从 ChromaDB 取 Top 30，然后过滤事件新闻。
   **⭐**❗**优化**：增量事件聚类.把“新闻 → 事件”的增量聚类做成了可重跑、可容错、带后处理（合并碎片 + 释放过期）的流水线，核心是**向量相似度 + 时间窗口 + 重要性门槛**三条件决定新闻归属，并保证事件统计和代表新闻始终一致。

   1. **增量聚类**：按发布时间逐条处理 `embedded` 新闻，用**向量近邻 + 3 天时间窗口 + 相似度 ≥0.75 找归属事件**，找不到就新建候选事件。

   2. **重要性过滤**：`importance` 太低的新闻不参与聚类，直接标 `unclustered`，避免低价值新闻进事件。

   3. **维护事件信息**：每次归属后重算事件的新闻数、时间范围、重要性，并选代表新闻同步事件名。

   4. **合并碎片**：主聚类后把只有 1 条新闻的候选事件，按相似度 ≥0.65 并入附近已有事件，减少碎片。

   5. **释放过期小事件**：时间窗口已过、仍不足 `MIN_EVENT_SIZE` 且重要性低的小事件，其新闻标回 `unclustered`，不再等。

   6. **容错批量入口**：单条事务、逐条异常捕获，最后输出新增/加入/跳过/合并/释放等统计。

   **`unclustered` 状态有什么用**

   - **语义清晰：** `clustered` 表示"已归入某个事件"，`unclustered` 表示"聚类阶段处理过，但没进任何事件"。不然 `clustered` 要同时代表两种含义。
   - **统计准确：** 查 `clustered` 的数量就是真的在事件里的新闻，不用每次都 `EXISTS (SELECT 1 FROM event_news ...)`。
   - **可回溯：** 以后调低阈值时，可以精确地把这批新闻放回流水线重跑：

7. 日报生成 **report_task**

   目前：日报里的 `events` 是 **LLM 现场聚类 + 总结的产物**，和 `events` 表、`event_news` 表**没有直接关系**。

   原来的逻辑：news 表 → 获取当天新闻 → LLM 自己识别事件 → 生成日报

   ⭐**❗优化：**SQLite 提供已聚类事件，LLM 分批生成事件摘要，再汇总成日报，最后统一保存并更新新闻状态。把"当天事件 + 新闻"变成结构化的日报 JSON：**读数据 → 分层选事件 → 分批调 LLM → 严格校验 → 补真实新闻 → 事务保存并标记新闻**，强调不编造、不跨事件、可重试、可幂等跳过。

   ```mermaid
   flowchart TD
       A[确定日报日期] --> B[读取当天事件与新闻]
       B --> C{有事件?}
       C -- 否 --> D[跳过, 返回 None]
       C -- 是 --> E{已有日报且无新新闻?}
       E -- 是 --> F[直接返回已有日报]
       E -- 否 --> G[分批调 LLM 生成事件解读]
       G --> H[生成日报总览]
       H --> I[校验 + 补全真实新闻]
       I --> J[事务保存日报 + 标记新闻为 reported]
       J --> K[返回日报]
   ```

8. 质量检测（新增）  **quality_check_task**

   作用是**在日报生成后自动做一次“聚类合理性 + 数字真实性”的抽查，有问题只记警告、不阻断流程**

日报质量检查（无 LLM、无新表，只告警不改数据）：

1. 事件内聚度：用事件的全部新闻向量评估聚类是否合理，用来校准聚类阈值
2. 数字溯源：日报总结里出现的数字必须能在来源新闻里找到，防止编造

**质量检测作为调参工具有用，作为每天常驻的步骤性价比低。**

**有用的部分：**

- **向量内聚度**（第一层）几乎零成本，直接用 Chroma 已有向量。它能量化你的 `EVENT_THRESHOLD=0.75` 和 `MERGE_THRESHOLD=0.65` 是否合理：内聚度长期偏低说明阈值太松。刚改了聚类逻辑（并入单条事件、阈值 0.65），正好需要它来观察效果。

**价值有限的部分：**

- **LLM 评审事件和相关性**每天最多 20 多次调用，只写日志和表，不反馈到任何流程，没人看就等于白花钱。
- **事件评审**：现在事件是程序聚类的，LLM 日报阶段不能再合并，误并只可能来自向量阈值。第一层内聚度已经能发现大部分问题。
- **领域相关性**：这本该由**分析阶段的 importance/category 解决**。加了 `importance > 3` 过滤后，不相关新闻进日报的概率已经下降。

### vector_store.py	

聚类写入的是 `ai_news`，`quality.py` 却去读 `news_embeddings`。如果 `news_embeddings` 里没有这批新闻的向量，内聚度检查会一直拿到空结果，而且只打一行 stderr 警告，你很可能一直没发现。

**统一方案：** 以 `embedding/vector_store.py` 为唯一入口（单例，同一个 Chroma client 和集合）。`storage/vectorstore.py` 退化为 LangChain 适配层，复用同一个 client 和集合，只给 MCP 检索用。

## 2.backend（11.04）

API / Router：负责接收请求和返回响应。

Service：负责具体业务逻辑。

Storage / DB：负责数据库连接和数据操作。

FastAPI 项目通常采用分层架构。Router 负责接收 HTTP 请求和参数校验，Service 负责业务逻辑，DB 或 Storage 层负责数据访问。通过 APIRouter 将不同业务模块的路由拆分，再通过 include_router 注册到主应用中。这样可以降低代码耦合，提高可维护性。

### api/     

 **路由层（Controller）** 接口层 定义 HTTP 接口，接收前端请求，返回响应。

按业务域拆分路由模块（`news.py`、`dashboard.py`、`sources.py`、`events.py`、`trends.py`）。每个文件用 `APIRouter` 定义一组 URL 接口，**只负责接收请求、参数校验、调用 service、返回响应**，不写复杂业务逻辑。`main.py` 里的 `include_router` 就是把它们挂载进来。

### schemas/    

**数据模型层  空**  

放 Pydantic 模型（`BaseModel`），定义**请求体、响应体、查询参数**的结构与校验规则。把 schema 单独放，使路由文件更干净，也让请求/响应契约集中可查。

**模型直接写在路由/入口文件里**

### services/   

**业务逻辑层（Service）**

核心业务都在这。`event_service.py` 处理事件相关逻辑，`news_service.py` 处理新闻相关逻辑（查询、清洗、组装、去重等）。**路由层调用 service，service 再调用 `storage/db.py` 访问数据库**。这样业务逻辑可被路由、Prefect 任务、脚本、测试复用，也便于单元测试。

### deos.py

**依赖管理   **   定义可复用的依赖，例如数据库连接、公共服务对象等。   get_db() 等，供各路由 Depends 使用

`storage/db.py` 负责“怎么连数据库”，`deps.py` 负责“FastAPI 怎么使用这个连接（生命周期管理、注入）”

### main.py

应用总入口。创建 FastAPI 实例，注册路由，配置 CORS 等。

负责创建 `FastAPI` 实例、配置 CORS、`include_router` 注册各子路由、`lifespan` 启动/关闭逻辑（初始化 Agent、建索引），以及部分直接定义在入口的接口（如问答、日报）。**它不该塞业务逻辑**，主要负责"装配"。

项目的 FastAPI 后端主入口。它主要负责**应用初始化、路由注册、请求处理、Agent 调用和日报数据查询**。

#### 1. lifespan

生命周期管理：

- 启动时调用 `init_db()` 建索引（幂等）。
- 初始化问答 Agent（`agent.graph.init_agent()`，内部完成 MCP stdio 连接 + 编译 LangGraph 图），只做一次，挂到 `app.state.agent`。
- 初始化失败不阻断启动，打印完整堆栈并将 `app.state.agent = None`，后续相关接口返回 503。
- 关闭时调用 `close_agent()` 释放 MCP 持久会话。

#### 2. 5个路由

路由（Route）就是把 HTTP 请求映射到 Python 函数

- `news`：新闻列表/详情/筛选
- `dashboard`：仪表盘聚合数据
- `sources`：RSS 源管理
- `events`：事件相关
- `trends`：趋势统计

**路由注册：**

1. 直接在 main.py 注册     @app.post("/api/ask")
2. 使用 APIRouter 拆分路由   app.include_router(news_router)

不是前端直接调用 `news_router`，而是 **FastAPI 先通过 `include_router()` 注册路由，前端再通过 HTTP 请求访问这些路由对应的 URL。**

`include_router()` 将其他模块定义的路由注册到 FastAPI 应用中。

这样拆分的好处是：

- `main.py` 负责应用入口。
- `news.py` 负责新闻接口。
- `events.py` 负责事件接口。
- `dashboard.py` 负责仪表盘接口。

这是后端常见的模块化路由设计。  

**模块负责定义接口，主应用负责统一注册，前端负责请求接口。**

###  `services/` 

**—— API 请求服务层**

**这是前端和 FastAPI 后端通信的地方。**  组织前端调用后端的 API。

主要负责：

1. 发送 HTTP 请求。
2. 封装后端 API。
3. 处理请求参数。

## 5.embedding（11.06）

 Embedding 代码主要集中在两个文件：

| 文件                        | 主要职责                                             |
| --------------------------- | ---------------------------------------------------- |
| `embedding/embed_news.py`   | 负责文本构造、调用模型、并发处理、失败重试、状态更新 |
| `embedding/vector_store.py` | 负责向量数据库的初始化、向量写入和检索               |

### 1. 并发处理：线程池提高 Embedding 请求效率

你的代码采用的是 `ThreadPoolExecutor`，核心思路是：

- 主线程从 SQLite 查询待处理新闻。
- 将每条新闻提交给线程池。
- 工作线程执行 `_embed_one(row)`，构造文本并请求 Embedding 模型。
- 主线程收集结果，再统一写入 Chroma 和更新 SQLite。

**为什么使用多线程？**

Embedding 的主要耗时通常是等待远程 API 返回结果，属于 I/O 密集型任务。

如果串行处理，每条新闻都要等待上一次 API 请求完成；使用线程池可以让多个请求同时进行，减少等待时间。

### 2. 失败重试：区分单次运行重试和跨运行失败次数

你的代码有两层重试控制。

**第一层：单次任务内部重试**

`_embed_one(row)` 中调用 Embedding 接口失败后，会根据 `MAX_RETRY=2` 进行重试。

这里要注意：`MAX_RETRY=2` 表示最多额外重试两次，所以总请求次数最多为 3 次。

另外，**在线客户端配置了 `max_retries=0`**(在线embedding模型设置），意味着不让 OpenAI SDK 自己再进行自动重试，而是由你的业务代码统一控制重试次数，避免两层重试叠加。

**第二层：跨运行失败次数限制**

它与单次任务内部的重试不是一回事。

例如：

- 今天第一次执行，某条新闻连续请求失败。
- 失败次数写入 SQLite。
- 下一次运行时，仍允许重新处理。
- 如果累计失败次数达到上限，就不再继续尝试。

**这样可以避免某条异常数据每次运行都无限消耗 API 资源。**

### 3. 状态更新：SQLite 记录处理进度

你的项目通过 `status` 字段记录新闻处理状态。

| 状态           | 含义                            |
| -------------- | ------------------------------- |
| `analyzed`     | 已完成 LLM 分析，等待 Embedding |
| `embed_failed` | Embedding 处理失败              |
| `embedded`     | Embedding 成功                  |

这里有一个比较重要的工程设计：

工作线程不直接操作 SQLite，数据库写入由主线程统一处理。为什么？

- SQLite 的连接和事务管理更容易集中控制。
- 避免多个工作线程同时使用同一个数据库连接。
- 让 API 请求和数据库写入职责分离。
- 方便统一进行批量提交。

> [!NOTE]
>
> **Embedding 并发处理与异常管理**
>
> 在 Embedding 阶段，我使用 Python 的 `ThreadPoolExecutor` 实现并发处理。
>
> 首先，主线程从 SQLite 中查询已经完成 LLM 分析、尚未完成向量化的新闻，然后将每条新闻提交到线程池。工作线程执行 `_embed_one()`，负责构造 Embedding 输入文本、调用模型 API，并返回新闻 ID、文本和向量结果。
>
> 由于 Embedding API 调用主要是 I/O 密集型操作，因此使用多线程可以让多个请求并发执行，提高整体处理效率。同时，我通过请求限流控制 API 调用频率，避免请求过于密集。
>
> 异常处理方面，我设计了两层机制：第一层是在**单条任务内部进行有限次数的重试**，最多请求三次；第二层是**通过 SQLite 记录失败次数**，限制**跨多次任务运行的累计失败次数**，避免异常数据被无限重复处理。
>
> 在数据写入方面，我将 Embedding 请求与数据库操作分离：工作线程只负责生成向量，主线程通过 `as_completed()` 获取完成结果，再将向量写入 Chroma，并更新 SQLite 中的处理状态。数据库采用批量提交方式，提高写入效率。
>
> 这种设计实现了**并发请求、失败恢复和处理状态追踪**，同时降低了多线程数据库访问带来的复杂性。

**1. 面试可能会问：为什么不直接对原始新闻全文进行 Embedding？**
我在项目中采用**标题、摘要、分类和关键词**构造 Embedding 输入，而不是直接使用全文。这样可以**减少冗余信息和无关内容，同时保留新闻的核心语义**。当然，如果摘要质量不高，也可能损失部分细节，需要通过检索评估来调整输入内容。

因为后续语义检索不仅需要计算相似度，还需要知道检索到的向量对应哪条新闻，以及新闻的标题、来源、时间等信息。

后续 RAG 检索过程可以：

1. 把用户问题转换成查询向量。
2. 在 Chroma 中寻找相似向量。
3. 通过对应的新闻 ID 找到新闻记录。
4. 获取新闻内容作为 LLM 的上下文。
5. 让 LLM 根据检索结果回答问题。

**3. Embedding 和 LLM 有什么区别？**

LLM 主要用于理解、推理和生成内容；Embedding 模型主要用于生成向量表示。你的项目分别用 LLM 分析新闻、用 Embedding 将新闻转换为向量。

**4.为什么同时使用 SQLite 和 Chroma？**

SQLite 保存新闻业务数据和处理状态；Chroma 保存向量及检索所需信息。两者分工不同，前者负责业务管理，后者负责向量检索。

>
> 在我的 AI 资讯项目中，Embedding 主要用于将新闻转换为向量，支持后续的语义检索和 RAG。

### Chroma /ˈkrəʊmə/

**Collection（集合）**：可以把它理解成数据库中的一张逻辑表。

`metadata={"hnsw:space": "cosine"}`指定向量索引使用余弦距离。

- **`hnsw`**: 代表 **Hierarchical Navigable Small World**（分层导航小世界图）。这是目前主流向量数据库（如 Chroma, Milvus, Faiss）用于加速近似最近邻搜索（ANN）的核心算法。它能让检索速度比暴力搜索快几个数量级。
- **`space`**: 指的是“距离空间”或“度量标准”，即如何定义两个向量之间的“远近”。
- **`cosine`**: 指**余弦相似度**。它不看向量的长度（模长），只看向量在空间中的**方向夹角**。

$$
余弦相似度：
\operatorname{cos}(A,B)=
\frac{A\cdot B}{\|A\|\|B\|}
。它衡量两个向量方向的接近程度
$$

- 越接近 1，方向越相似。
- 越接近 0，方向越不相似。
- 越接近 -1，方向越相反。

Chroma 配置的是 `cosine` 距离，查询结果中的距离通常是：
$$
d(A,B)=1-\operatorname{cos}(A,B)
$$
**所以距离越小，越相似**

- **余弦相似度：**

$$
\operatorname{cos}(A,B)=
\frac{A\cdot B}{\|A\|\|B\|}
$$

取值通常在 -1 到 1 之间，越接近 1 表示方向越接近。

- **欧氏距离： **   欧氏距离就是**<u>逐维度</u>做差、平方、求和、开方**：

$$
d(A,B)=\sqrt{\sum_{i=1}^{n}(A_i-B_i)^2}
$$

距离越小，两个向量越接近。i=0---n   n维向量 

- **内积：**

$$
A\cdot B=\sum_{i=1}^{n}A_iB_i
$$

**内积越大，数值越大**，但它同时受到向量方向和长度影响。
