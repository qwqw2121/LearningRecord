## 一、学习内容与记录

### 1. RAG 为什么出现？

**定义：**

RAG（Retrieval-Augmented Generation，检索增强生成）是一种将外部知识检索与大语言模型生成结合起来的技术。

它不是让模型只依赖训练阶段学到的知识回答，而是在生成答案前，从外部知识库检索相关内容，再将检索结果作为上下文提供给模型。

**目的：**

主要解决：
- 模型训练知识可能过时。
- 模型不了解企业或个人私有数据。
- 直接依赖模型回答容易产生幻觉。
- 通过重新训练模型更新知识成本较高。

例如，用户询问：

```text
最近一周有哪些值得关注的 AI Agent 新闻？
```

通用 LLM 不一定知道用户自己的新闻数据库中有哪些内容。

RAG 可以先从项目知识库中检索新闻，再让模型基于检索结果总结。

**原理：**

RAG 可以分为两个阶段：

**离线阶段：知识库构建**

```text
文档加载
  ↓
文本清洗
  ↓
文本切分
  ↓
Embedding
  ↓
向量数据库
```

**在线阶段：检索与生成**

```text
用户问题
  ↓
Query Embedding
  ↓
向量检索
  ↓
获取相关文档
  ↓
构建 Prompt
  ↓
LLM 生成答案
  ↓
返回答案及来源
```

**实践：**

AI 资讯项目将新闻作为外部知识源。

离线阶段：
1. RSS 采集新闻。
2. 清洗和提取正文。
3. 使用 LLM 分析新闻。
4. 生成 Embedding。
5. 将向量写入 Chroma。

在线阶段：
1. 用户提出问题。
2. Agent 调用新闻语义检索工具。
3. 检索模块从 Chroma 中获取相关新闻。
4. 将新闻标题、摘要和来源等信息返回。
5. Agent 根据检索结果组织答案。

**局限与取舍：**

RAG 可以让模型参考外部知识，但不能保证答案一定正确。

如果检索结果本身错误、过时或不相关，模型仍然可能生成错误答案。

RAG 也不能完全解决模型推理能力不足的问题。

### 2. 文档加载、文本切分、Embedding、向量检索、上下文拼接、LLM 生成

**定义：**

这是 RAG 的核心处理链路：

- 文档加载：获取原始文档。
- 文本切分：将较长文档拆分成较小文本块。
- Embedding：将文本块转换为向量。
- 向量检索：根据问题向量找到相关文本块。
- 上下文拼接：将检索结果组织成 Prompt。
- LLM 生成：模型根据问题和检索内容生成答案。

**目的：**

将分散的外部知识组织成可检索的知识库，并在用户提问时找到相关内容，辅助模型回答。

**原理：**

完整流程：

1. 文档加载：读取 PDF、网页、数据库记录等内容。
2. 文本切分：根据长度或语义边界拆分文本。
3. Embedding：对每个文本块生成向量。
4. 向量检索：对用户问题生成向量，计算与知识库向量的距离。
5. 上下文拼接：将检索到的文本和用户问题组合。
6. LLM 生成：模型基于上下文生成最终回答。

示例 Prompt：

```text
你是一个 AI 新闻分析助手。

请根据以下检索内容回答用户问题。
如果检索内容无法支持答案，请明确说明。

检索内容：
{context}

用户问题：
{question}

请给出答案，并标注相关来源。
```

**实践：**

项目中新闻数据已经经过采集、清洗、分析和向量化。

在线查询时，通过语义检索工具获取新闻内容，再交给 Agent 组织回答。

需要区分：项目的原始新闻处理链路与在线 RAG 查询链路。新闻采集和入库属于知识库构建过程，不是每次用户提问时都重新执行。

**局限与取舍：**

每个环节都可能影响最终答案：
- 文档加载不完整，后续无法检索到缺失内容。
- 切分不合理，可能破坏上下文。
- Embedding 表达不准确，可能影响召回。
- 检索结果不相关，会影响生成。
- Prompt 组织不合理，模型可能忽略关键信息。

### 3. Chunk Size 和 Chunk Overlap

**定义：**

Chunk Size 是文本切分后每个文本块的目标大小。

Chunk Overlap 是相邻文本块之间重复保留的内容长度。

例如：

```text
原文：A B C D E F G H

Chunk Size = 4
Chunk Overlap = 1

Chunk 1：A B C D
Chunk 2：D E F G
Chunk 3：G H
```

这里仅用字符示意，实际切分可能按 Token、字符或其他单位进行。

**目的：**

长文本通常不能无限制地直接输入 Embedding 模型，因此需要切分。

Overlap 可以减少文本刚好在切分边界处被拆开，导致上下文信息丢失的问题。

**原理：**

切分时：
1. 按照设定的长度拆分文档。
2. 每个 Chunk 保存一段文本。
3. 相邻 Chunk 保留部分重叠内容。
4. 分别生成 Embedding。
5. 检索时返回相关 Chunk。

**实践：**

项目主要处理新闻数据。

一篇新闻通常包含标题、正文、发布时间、来源等信息。

如果新闻正文较短，可以直接将整篇新闻作为一个检索单元，不一定需要再切分。

如果新闻正文较长，可以按段落或 Token 长度切分，同时保留新闻 ID、标题、发布时间等元数据。

**局限与取舍：**

Chunk Size 太小：
- 语义不完整。
- 检索结果可能缺少上下文。

Chunk Size 太大：
- 可能包含多个主题。
- 检索精度可能下降。
- Embedding 输入长度和计算成本增加。

Overlap 太大：
- 重复内容增多。
- 增加向量存储和检索成本。

Chunk Size 和 Overlap 应结合文档结构、模型限制和检索效果进行调整。

### 4. 混合检索、Rerank、Query Rewrite

**定义：**

这三种技术都是 RAG 检索阶段常见的优化方式。

- 混合检索：结合关键词检索和向量检索。
- Rerank：对初步检索结果进行二次排序。
- Query Rewrite：改写用户问题，让它更适合检索。

**目的：**

向量检索并不是所有情况下都能找到最合适的内容。

例如：
- 专有名词、新闻标题、事件编号可能更适合关键词检索。
- 语义相近但表达不同的问题适合向量检索。
- 初步检索结果可能相关性不够高，需要重新排序。

**原理：**

混合检索：

```text
用户问题
  ├── 关键词检索
  └── 向量检索
        ↓
     结果融合
        ↓
     返回候选文档
```

Rerank：

```text
用户问题
  ↓
初步检索 Top-N
  ↓
Rerank 模型计算相关性
  ↓
重新排序
  ↓
选取 Top-K
```

Query Rewrite：

```text
原始问题：
最近大模型有什么进展？

改写问题：
最近一周大语言模型领域有哪些重要技术发布和产品进展？
```

改写后再进行检索。

**实践：**

项目目前使用新闻语义检索能力，可以通过 Embedding 和向量检索找到语义相关的新闻。

混合检索、Rerank 和 Query Rewrite 可以作为后续优化方向。不能将尚未实现的功能描述为项目已有能力。

**局限与取舍：**

- 混合检索需要设计不同检索结果的融合方式。
- Rerank 会增加模型调用和响应延迟。
- Query Rewrite 可能改变用户原本意图。
- 增加检索模块不一定能提升最终答案质量。

应通过评估集比较优化前后的 Recall、MRR、延迟和成本。

### 5. RAG 如何减少幻觉？

**定义：**

幻觉是指大语言模型生成了看似合理，但实际上缺乏事实依据或与真实信息不符的内容。

RAG 通过向模型提供外部检索内容，为回答增加事实参考。

**目的：**

减少模型仅依靠参数记忆生成答案的情况，提高回答的可追溯性和事实依据。

**原理：**

普通 LLM：

```text
用户问题 → LLM → 答案
```

RAG：

```text
用户问题
  ↓
检索相关资料
  ↓
将资料作为上下文
  ↓
LLM 根据上下文生成答案
```

可以在 Prompt 中增加约束：

- 仅根据检索内容回答。
- 缺少证据时明确说明。
- 对关键结论提供来源。
- 不要编造不存在的新闻和数据。

**实践：**

项目中的新闻查询结果包含新闻标题、来源、发布时间等信息。

Agent 可以基于检索结果回答问题，并提供新闻来源。

对于知识库中不存在的新闻，应明确说明未检索到相关内容，而不是编造新闻。

**局限与取舍：**

RAG 只能提供参考依据，不能自动保证事实正确。

还需要关注：
- 原始数据是否真实。
- 检索结果是否相关。
- 新闻发布时间是否符合查询范围。
- 模型是否忠实使用检索内容。
- 引用来源是否真实存在。

### 6. RAG 常见问题及优化方式

**定义：**

RAG 的最终效果由知识库质量、检索质量和生成质量共同决定。

常见问题包括：
- 检索不到相关文档。
- 检索结果不相关。
- 文档切分破坏上下文。
- 召回内容过多或过少。
- 模型忽略检索内容。
- 答案没有正确引用来源。

**目的：**

通过定位问题所在的环节，有针对性地优化 RAG，而不是只修改 Prompt。

**原理：**

可以将问题分成三个阶段：

1. 知识库阶段：数据是否完整、清洗是否合理、Embedding 是否成功。
2. 检索阶段：是否召回正确文档、Top-K 是否合理、排序是否准确。
3. 生成阶段：模型是否根据上下文回答、引用是否正确、是否存在无依据推断。

常见优化方式：

| 问题 | 优化方式 |
|---|---|
| 数据缺失 | 检查采集、清洗和入库流程 |
| 检索不到 | 调整 Embedding、检索策略 |
| 结果不相关 | 混合检索、Rerank |
| 上下文不完整 | 调整 Chunk Size、Overlap |
| 答案编造 | Prompt 约束、证据校验 |
| 引用错误 | 对引用 ID 和来源进行校验 |

**实践：**

项目已经有基础检索评估，可以使用测试问题检查检索结果。

例如：
- 查询某个具体 AI 公司近期新闻。
- 查询某一时间范围内的大模型新闻。
- 查询 AI Agent 相关技术进展。

可以记录正确新闻是否出现在 Top-5 中，并观察排序情况。

**局限与取舍：**

优化 RAG 需要通过数据验证，不能只凭主观感觉。

增加 Rerank、混合检索等模块会增加系统复杂度和延迟，应先定位瓶颈，再决定是否引入。
