## 一、学习内容与记录

### 1. RAG 为什么出现？

**定义：**

RAG（Retrieval-Augmented Generation，检索增强生成）是一种将**外部知识检索与大语言模型生成**结合起来的技术。

它不是让模型只依赖训练阶段学到的知识回答，而是在生成答案前，从**外部知识库**检索相关内容，再将检索结果作为上下文提供给模型。

**目的：**

主要解决：
- 模型训练知识可能过时。
- 模型不了解企业或个人私有数据。
- 直接依赖模型回答容易产生幻觉。
- 通过重新训练模型更新知识成本较高。

例如，用户询问：

```text
最近一周有哪些值得关注的 AI Agent 新闻？
```

通用 LLM 不一定知道用户自己的新闻数据库中有哪些内容。

RAG 可以先从项目知识库中检索新闻，再让模型基于检索结果总结。

**原理：**

RAG 可以分为两个阶段：

**离线阶段：知识库构建**

```text
文档加载
  ↓
文本清洗
  ↓
文本切分
  ↓
Embedding
  ↓
向量数据库
```

**在线阶段：检索与生成**

```text
用户问题
  ↓
Query Embedding
  ↓
向量检索
  ↓
获取相关文档
  ↓
构建 Prompt
  ↓
LLM 生成答案
  ↓
返回答案及来源
```

**实践：**

AI 资讯项目将新闻作为外部知识源。

离线阶段：
1. RSS 采集新闻。
2. 清洗和提取正文。
3. 使用 LLM 分析新闻。
4. 生成 Embedding。
5. 将向量写入 Chroma。

在线阶段：
1. 用户提出问题。
2. Agent 调用新闻语义检索工具。
3. 检索模块从 Chroma 中获取相关新闻。
4. 将新闻标题、摘要和来源等信息返回。
5. Agent 根据检索结果组织答案。

**局限与取舍：**

RAG 可以让模型参考外部知识，但不能保证答案一定正确。

如果检索结果本身错误、过时或不相关，模型仍然可能生成错误答案。

RAG 也不能完全解决模型推理能力不足的问题。

### 2. 文档加载、文本切分、Embedding、向量检索、上下文拼接、LLM 生成

**定义：**

这是 RAG 的核心处理链路：

- 文档加载：获取原始文档。
- 文本切分：将较长文档拆分成较小文本块。
- Embedding：将文本块转换为向量。
- 向量检索：根据问题向量找到相关文本块。
- 上下文拼接：**将检索结果组织成 Prompt**。
- LLM 生成：模型根据问题和检索内容生成答案。

**目的：**

将分散的外部知识组织成可检索的知识库，并在用户提问时找到相关内容，辅助模型回答。

**原理：**

完整流程：

1. 文档加载：读取 PDF、网页、数据库记录等内容。
2. 文本切分：根据长度或语义边界拆分文本。
3. Embedding：对每个文本块生成向量。
4. 向量检索：对用户问题生成向量，计算与知识库向量的距离。
5. 上下文拼接：将检索到的文本和用户问题组合。
6. LLM 生成：模型基于上下文生成最终回答。

示例 Prompt：

```text
你是一个 AI 新闻分析助手。

请根据以下检索内容回答用户问题。
如果检索内容无法支持答案，请明确说明。

检索内容：
{context}

用户问题：
{question}

请给出答案，并标注相关来源。
```

**实践：**

项目中新闻数据已经经过采集、清洗、分析和向量化。

在线查询时，通过语义检索工具获取新闻内容，再交给 Agent 组织回答。

需要区分：项目的原始新闻处理链路与在线 RAG 查询链路。新闻采集和入库属于知识库构建过程，不是每次用户提问时都重新执行。

**局限与取舍：**

每个环节都可能影响最终答案：
- 文档加载不完整，后续无法检索到缺失内容。
- **切分不合理，可能破坏上下文**。
- Embedding 表达不准确，可能影响召回。
- 检索结果不相关，会影响生成。
- Prompt 组织不合理，模型可能忽略关键信息。

### 3. Chunk Size 和 Chunk Overlap

**定义：**

Chunk Size 是文本切分后**每个文本块的目标大小**。

Chunk Overlap 是相邻文本块之间**重复保留的内容长度**。

例如：

```text
原文：A B C D E F G H

Chunk Size = 4
Chunk Overlap = 1

Chunk 1：A B C D
Chunk 2：D E F G
Chunk 3：G H
```

这里仅用字符示意，实际切分可能按 Token、字符或其他单位进行。

**目的：**

长文本通常不能无限制地直接输入 Embedding 模型，因此需要切分。

Overlap 可以减少文本刚好在切分边界处被拆开，导致上下文信息丢失的问题。

**原理：**

切分时：
1. 按照设定的长度拆分文档。
2. 每**个 Chunk 保存一段文本**。
3. **相邻 Chunk 保留部分重叠内容**。
4. 分别生成 Embedding。
5. 检索时返回相关 Chunk。

**实践：**

项目主要处理新闻数据。

一篇新闻通常包含标题、正文、发布时间、来源等信息。

如果新闻正文较短，可以直接将整篇新闻作为一个检索单元，不一定需要再切分。

如果新闻正文较长，可以按段落或 Token 长度切分，同时保留新闻 ID、标题、发布时间等元数据。

**局限与取舍：**

Chunk Size 太小：
- 语义不完整。
- 检索结果可能缺少上下文。

Chunk Size 太大：
- 可能包含多个主题。
- 检索精度可能下降。
- Embedding 输入长度和计算成本增加。

Overlap 太大：
- 重复内容增多。
- 增加向量存储和检索成本。

Chunk Size 和 Overlap 应结合文档结构、模型限制和检索效果进行调整。

### 4. 混合检索、Rerank、Query Rewrite

**定义：**

这三种技术都是 RAG 检索阶段常见的**优化方式**。

- 混合检索：结合**关键词**检索和**向量**检索。
- Rerank：对**初步检索结果进行二次排序**。
- Query Rewrite：改写用户问题，让它更适合检索。

**目的：**

向量检索并不是所有情况下都能找到最合适的内容。

例如：
- 专有名词、新闻标题、事件编号可能更适合关键词检索。
- 语义相近但表达不同的问题适合向量检索。
- 初步检索结果可能相关性不够高，需要重新排序。

**原理：**

混合检索：

```text
用户问题
  ├── 关键词检索
  └── 向量检索
        ↓
     结果融合
        ↓
     返回候选文档
```

Rerank：

用户问题
  ↓
初步检索 Top-N
  ↓
**Rerank 模型计算相关性**
  ↓
**重新排序**
  ↓
选取 Top-K

Query Rewrite：

```text
原始问题：
最近大模型有什么进展？

改写问题：
最近一周大语言模型领域有哪些重要技术发布和产品进展？
```

改写后再进行检索。

**实践：**

项目目前使用新闻语义检索能力，可以通过 Embedding 和向量检索找到语义相关的新闻。

混合检索、Rerank 和 Query Rewrite 可以作为后续优化方向。不能将尚未实现的功能描述为项目已有能力。

**局限与取舍：**

- 混合检索需要设计不同检索结果的融合方式。
- Rerank 会增加模型调用和响应延迟。
- Query Rewrite 可能改变用户原本意图。
- 增加检索模块不一定能提升最终答案质量。

应通过评估集比较优化前后的 **Recall、MRR、延迟和成本**。

### 5. RAG 如何减少幻觉？

**定义：**

幻觉是指大语言模型生成了**看似合理，**但实际上**缺乏事实依据或与真实信息不符**的内容。

RAG 通过向模型提供**外部检索内容，为回答增加事实参考**。

**目的：**

减少模型仅依靠**参数记忆**生成答案的情况，提高回答的可追溯性和事实依据。

**原理：**

普通 LLM：

```text
用户问题 → LLM → 答案
```

RAG：

```text
用户问题
  ↓
检索相关资料
  ↓
将资料作为上下文
  ↓
LLM 根据上下文生成答案
```

可以在 Prompt 中增加约束：

- 仅根据检索内容回答。
- 缺少证据时明确说明。
- 对关键结论提供来源。
- 不要编造不存在的新闻和数据。

**实践：**

项目中的新闻查询结果包含新闻标题、来源、发布时间等信息。

Agent 可以基于检索结果回答问题，并提供新闻来源。

对于知识库中不存在的新闻，应明确说明未检索到相关内容，而不是编造新闻。

**局限与取舍：**

RAG 只能提供参考依据，不能自动保证事实正确。

还需要关注：
- **原始数据是否真实**。
- 检索结果**是否相关**。
- 新闻发布**时间是否符合查询范围**。
- **模型是否忠实使用检索内容**。
- **引用来源是否真实存在**。

### 6. RAG 常见问题及优化方式

**定义：**

RAG 的最终效果由**知识库质量、检索质量和生成质量**共同决定。

常见问题包括：
- 检索不到相关文档。
- 检索结果不相关。
- 文档切分破坏上下文。
- 召回内容过多或过少。
- 模型忽略检索内容。
- 答案没有正确引用来源。

**目的：**

通过定位问题所在的环节，有针对性地优化 RAG，而不是只修改 Prompt。

**原理：**

可以将问题分成三个阶段：

1. **知识库阶段**：数据是否完整、清洗是否合理、Embedding 是否成功。
2. **检索阶段**：是否召回正确文档、Top-K 是否合理、排序是否准确。
3. **生成阶段**：模型是否根据上下文回答、引用是否正确、是否存在无依据推断。

常见优化方式：

| 问题 | 优化方式 |
|---|---|
| 数据缺失 | 检查采集、清洗和入库流程 |
| 检索不到 | 调整 Embedding、检索策略 |
| 结果不相关 | 混合检索、Rerank |
| 上下文不完整 | 调整 Chunk Size、Overlap |
| 答案编造 | Prompt 约束、证据校验 |
| 引用错误 | 对引用 ID 和来源进行校验 |

**实践：**

项目已经有基础检索评估，可以使用测试问题检查检索结果。

例如：
- 查询某个具体 AI 公司近期新闻。
- 查询某一时间范围内的大模型新闻。
- 查询 AI Agent 相关技术进展。

可以记录正确新闻是否出现在 Top-5 中，并观察排序情况。

**局限与取舍：**

**优化 RAG 需要通过数据验证**，不能只凭主观感觉。

增加 Rerank、混合检索等模块会增加系统复杂度和延迟，应先定位瓶颈，再决定是否引入。
### 7.混合检索如何融合关键词检索和向量检索结果？
1. 为什么需要混合检索？
  两种检索方式各有优势。
| 对比 | 关键词检索 BM25      | 向量检索                       |
| ---- | -------------------- | ------------------------------ |
| 原理 | 词项匹配、词频统计   | Embedding 向量相似度           |
| 擅长 | 专有名词、精确关键词 | 语义相似、同义表达             |
| 优势 | 精确匹配能力强       | 能理解语义关联                 |
| 局限 | 不容易识别同义表达   | 可能召回主题相似但不相关的内容 |

例如用户搜索：「OpenAI 最新 Agent 产品」
关键词检索可能找到**标题包含 OpenAI、Agent 的新闻**。
向量检索可能找到**没有出现这些关键词**，但**实际讨论 OpenAI Agent 产品的新闻**。
两者结合，可以提高召回覆盖率。
2. 常见融合算法
**方法一：加权分数融合（Weighted Score Fusion）**
直接将两种检索的分数归一化，再加权求和。
公式：
\[
Score(d)=\alpha S_{BM25}(d)+(1-\alpha)S_{Vector}(d)
\]
其中：
- \(S_{BM25}\)：关键词检索归一化分数。
- \(S_{Vector}\)：向量检索归一化分数。
- \(\alpha\)：关键词检索权重。
缺点：BM25 和向量相似度的分数分布不同，需要先进行归一化，而且权重需要调优。

**方法二：RRF（Reciprocal Rank Fusion）**  ，倒数排名融合
RRF 是最常见、也很适合你当前项目的融合方式。
它不比较原始分数，而是根据**文档在不同检索结果中的排名**计算融合分数。
公式：
\[
RRF(d)=\sum_{r\in R}\frac{1}{k+rank_r(d)}
\]
- \(d\)：候选文档。
- \(R\)：检索结果集合。
- \(rank_r(d)\)：文档在某一路检索中的排名。
- \(k\)：平滑常数，通常取 60。
RRF 的优点：
- 不需要统一两种检索的原始分数。
- 不需要复杂的权重训练。
- 能够融合多路检索结果。
- 实现简单，鲁棒性较好。

**方法三：加权 RRF（Weighted RRF）**
如果你认为关键词检索比向量检索更重要，可以给两路排名设置不同权重：
\[
WRRF(d)=
\frac{w_1}{k+rank_1(d)}
+
\frac{w_2}{k+rank_2(d)}
\]
例如：
- BM25 权重：0.4
- Vector 权重：0.6

### 6. Rerank 为什么可以改善排序？
1. 为什么向量检索排序不够准确？
你目前使用 DashScope text-embedding-v3，属于双编码器（Bi-Encoder）检索思路。
Query 和 News 分别转换成向量，再计算相似度。
这种方式速度快，因为新闻向量可以提前计算并存储。
但存在一个问题：Query 和 News 在计算相似度时，没有进行深度的交互分析。
2. Rerank 的工作原理
Rerank 常用 Cross-Encoder（交叉编码器）。
它将 Query 和每篇候选新闻拼接后，一起输入模型：
Query + News A ──> Rerank ──> 0.96
Query + News B ──> Rerank ──> 0.42
Query + News C ──> Rerank ──> 0.75
为什么效果更好？
因为 **Cross-Encoder 在模型内部可以通过 Attention 机制，让 Query 和 News 的 Token 进行交互**，从而更精细地判断：
- 新闻是否回答了用户的问题？
- 新闻中的实体是否与问题一致？
- 新闻是否符合用户的具体意图？
- 新闻是否只是主题相似，但实际上不相关？
注意：Rerank 分数通常是**相关性分数，不一定是经过校准的概率**。
三、常见 Rerank 算法和模型有哪些？
这里需要区分：有些是排序模型架构，有些是传统排序算法。

| 方法          | 核心原理                              | 特点                       |
| ------------- | ------------------------------------- | -------------------------- |
| Cross-Encoder | Query 和 Document 联合编码            | 精度较高，适合 Rerank      |
| MonoT5        | 使用 T5 模型判断文档相关性            | 将排序转化为文本生成任务   |
| ColBERT       | Late Interaction，计算 Token 级别匹配 | 兼顾效率和细粒度交互       |
| LLM Rerank    | 利用大模型判断文档相关性              | 灵活，但成本和延迟较高     |
| LambdaMART    | 基于梯度提升树优化排序指标            | 传统 Learning to Rank 方法 |

重点理解前三种：
1. Cross-Encoder
最常见的 Rerank 思路。
输入：
[CLS] Query [SEP] Document [SEP]
**模型联合计算两者的相关性**，输出一个分数。
代表：BGE Reranker、BCE Reranker。
2. ColBERT
不是把整个 Query 和 Document 压缩成单个向量比较，而是**保留 Token 级别的向量表示**，通过 MaxSim 等操作进行**细粒度匹配**。
优点是能够保留更多词语之间的匹配信息。
3. LLM Rerank
直接让大语言模型对候选文档进行相关性判断。优点是灵活，缺点是成本高、速度慢，而且输出稳定性需要控制。

 ### 三、学习复盘

**今天还没搞懂的内容：**

- RAG 和普通 LLM 调用的本质区别是什么？RAG 为什么不需要重新训练模型就能使用外部知识？
  - 普通 LLM：直接把**用户问题交给模型**，模型根据训练时学到的知识生成回答。
  - RAG：先从外部知识库检索相关资料，再把**资料和用户问题一起交给模型**生成回答。
  RAG 不需要重新训练模型，因为它不是修改模型参数，而是在**推理阶段动态提供外部知识**。

- 离线知识库构建和在线检索生成为什么要分开？哪些操作只需要执行一次，哪些操作需要在每次查询时执行？
    因为两者执行频率不同。
  - 离线：新闻入库或更新时执行，不需要每次查询都重新计算。
  - 在线：用户每次提问时执行。
  核心目的：避免重复计算 Embedding，降低查询延迟和成本。

| 离线知识库构建 | 在线检索生成    |
| -------------- | --------------- |
| 加载文档       | 接收用户问题    |
| 清洗数据       | Query Embedding |
| 文本切分       | 检索相关文档    |
| Embedding      | 结果排序        |
| 写入向量数据库 | 拼接上下文      |
| 更新索引       | LLM 生成回答    |

- 文本切分时，为什么不能只按照固定字符数机械地切分？如何保留新闻的标题、来源和上下文信息？
  因为**机械切分可能破坏语义完整性**。
  问题：
  - 标题和正文可能分离。
  - 句子可能被截断。
  - 上下文不完整。
  - 检索到的内容缺乏独立语义。
  建议：
  - 优先按照文章结构、段落、句子切分。
  - 每个 Chunk 保留**新闻 ID、标题、来源、发布时间等 Metadata**。
  - 检索时将标题与正文结合，增强上下文。
  
- Chunk Size 和 Chunk Overlap 如何影响召回率、检索精度和上下文长度？
Chunk Size 决定每个文本块的大小。Chunk 太小容易造成语义不完整，降低召回效果；太大则容易混入无关信息，影响检索精度，同时增加上下文长度和 Token 成本。
Chunk Overlap 是相邻文本块之间重复保留的内容，可以减少切分边界造成的信息丢失，提高上下文完整性。但 Overlap 太大也会增加重复内容和检索成本。
因此，需要根据文档类型、语义完整性和检索效果调整两者，而不是使用固定参数。

一句话记忆：Chunk Size 控制检索粒度，Chunk Overlap 控制上下文连续性。

| Chunk Size | 召回率   | 检索精度 | 上下文长度 |
| ---------- | -------- | -------- | ---------- |
| 太小       | 可能下降 | 可能下降 | 较短       |
| 适中       | 通常较好 | 通常较好 | 适中       |
| 太大       | 可能提高 | 可能下降 | 较长       |
Chunk 太小： 
  - 一段完整语义可能被拆开。
  - 重要信息和背景信息分离。
  - 检索到的**片段可能无法独立回答问题**。
Chunk 太大：
- 一个 Chunk 可能**包含多个不同主题**。
- Embedding 表达的是整段文本的综合语义。
- 无关内容可能干扰相似度计算。
- 即使只需要一小段信息，也可能返回大量无关内容。

| Chunk Overlap | 召回率           | 检索精度   | 上下文长度   |
| ------------- | ---------------- | ---------- | ------------ |
| 0             | 边界信息可能丢失 | 可能受影响 | 较短         |
| 适中          | 有助于提高       | 通常较稳定 | 略有增加     |
| 太大          | 不一定继续提高   | 可能下降   | 重复内容增加 |

Chunk Size 决定每次检索的文本粒度。
Chunk Overlap 决定相邻文本块之间保留多少上下文。
两者共同决定**检索结果的完整性和冗余程度**。

- 向量检索返回的 Top-K 文档为什么不一定都是最相关的？
  因为**向量相似度不等于真实相关性**。
  原因：
  - Embedding 只能表达语义相似程度。
  - 不一定理解问题中的**时间、实体和具体约束**。
  - 不同新闻可能讨论相似主题，但回答的问题不同。
  - Top-K 只是按照**相似度排序**，不代表每篇文档都具有回答价值。
  
- **混合检索如何融合关键词检索和向量检索结果？Rerank 为什么可以改善排序？**
  混合检索主要是结合**关键词检索和向量检索的优势**。关键词检索通常使用 BM25，擅长精确匹配；向量检索通过 Embedding 计算语义相似度，擅长理解不同表达之间的语义关联。
  两路检索结果可以通过 RRF（倒数排名融合）进行合并。RRF 不直接比较不同检索算法的原始分数，而是根据文档在各路检索中的排名计算融合分数。
  在此基础上，可以增加 Rerank 重排序。常见方式是使用 Cross-Encoder，将 Query 和候选 Document 一起输入模型，进行更细粒度的相关性判断，重新排序并保留 Top-K 文档。
  这样可以先通过混合检索提高召回覆盖率，再通过 Rerank 提高最终结果的排序质量。

  - 混合检索（Hybrid Search）：同时使用**关键词检索和向量检索**，提高相关文档的召回能力。
  - 结果融合（Fusion）：将**不同检索方式得到的结果合并**，解决排序分数不一致的问题。
  - Rerank（重排序）：对**召回的候选文档重新计算相关性**，改善最终排序。

- RAG 提供了检索内容后，模型为什么仍然可能产生幻觉？如何判断回答是否有证据支持？
  RAG 只能提供参考资料，不能保证**模型一定正确使用资料**。
  常见原因：
  1. 检索到的内容本身错误。
  2. 检索结果不完整。
  3. 上下文中存在相互矛盾的信息。
  4. 模型忽略证据，使用自身知识补充。
  5. 模型错误理解或推断了证据。
  减少幻觉的方法：
  - 提高数据质量。
  - 优化检索和重排序。
  - Prompt 要求基于证据回答。
  - 要求回答提供新闻 ID 或来源引用。
  - 对无法找到证据的问题明确回答不知道。
  - 对生成结果进行事实和引用校验。
    
- 如果检索结果正确，但最终回答错误，应该如何定位问题发生在检索阶段还是生成阶段？
  | 现象                               | 问题位置 | 排查方向                  |
| ---------------------------------- | -------- | ------------------------- |
| 正确新闻没有召回                   | 检索阶段 | Embedding、切分、召回策略 |
| 召回正确但排序靠后                 | 检索阶段 | RRF、Rerank               |
| 正确新闻已经进入上下文，但回答错误 | 生成阶段 | Prompt、上下文、模型推理  |
| 回答内容没有证据支持               | 生成阶段 | 忠实度、引用校验          |
| 原始新闻本身就有错误               | 数据阶段 | 数据清洗、来源质量        |

最简单的定位方法：

先检查检索结果，再检查最终传给 LLM 的上下文，最后检查模型输出。

  1. RAG 定义和背景
RAG（Retrieval-Augmented Generation，检索增强生成）是一种将外部知识检索与大语言模型生成结合的技术。

解决的问题：
- 模型训练知识存在时间限制。
- 专业领域知识不足。
- 私有知识无法直接通过预训练获得。
- 模型容易产生幻觉。
核心思想：先检索外部知识，再基于检索结果生成回答。
2. 完整 RAG 流程
离线阶段：知识库构建
1. 文档加载（Document Loader）
2. 数据清洗（Cleaning）
3. 文本切分（Chunking）
4. Embedding 向量化
5. 存储到向量数据库

在线阶段：检索与生成
1. 接收用户 Query
2. Query Embedding
3. 向量 / 关键词 / 混合检索
4. Rerank 重排序
5. 拼接检索上下文
6. LLM 生成回答
7. 引用与事实校验


| 技术          | 解决什么问题         | 关键词           |
| ------------- | -------------------- | ---------------- |
| BM25          | 关键词如何匹配       | 词频、逆文档频率 |
| Embedding     | 如何理解语义相似     | 向量、语义       |
| Hybrid Search | 如何提高召回覆盖率   | 多路召回         |
| RRF           | 如何融合不同检索结果 | 排名融合         |
| Rerank        | 如何提高排序准确性   | Cross-Encoder    |
| Query Rewrite | 如何优化用户查询     | 查询改写、扩展   |

最核心的逻辑：
- 混合检索：尽可能找到更多相关文档。
- RRF：把不同检索渠道的结果合并。
- Rerank：从候选文档中选出真正最相关的文档。
