## 一、学习内容与记录

### 1. RAG 检索评估：Recall@K 与 MRR

**定义：**

Recall@K 和 MRR 是常见的**检索效果评估指标**。

- Recall@K：前 K 个检索结果中，是否找到了相关文档，衡量相关文档的召回能力。
- MRR（Mean Reciprocal Rank）：第一个相关结果排名的倒数，再对多个查询取平均，衡量相关结果是否排在靠前位置。

**目的：**

判断向量检索是否能够找到正确的知识，以及相关结果是否出现在靠前的位置。

**原理：**
1. Recall@K  它关注的是：有没有把相关内容尽可能找全。
\[
Recall@K=\frac{\text{前K条检索结果中的相关文档数}}{\text{全部相关文档数}}
\]

2. MRR  它关注的是：用户能不能在靠前的位置看到相关内容。
公式： 
\[
MRR=\frac{1}{N}\sum_{i=1}^{N}\frac{1}{rank_i}
\]
其中 rank 是第一个相关结果所在的位置。

假设某个查询的相关文档排名如下：

```text
Top 5:
1. 不相关
2. 不相关
3. 相关
4. 不相关
5. 不相关
```

那么：

- Recall@5：如果只有一个相关文档需要找回，则为 1。
- Reciprocal Rank：第一个相关结果排在第 3 位，因此为 1/3。

多个查询的 Reciprocal Rank 取平均，就是 MRR。

**实践：**

AI 资讯项目曾使用少量查询进行检索评估，当前记录的测试结果为：

- Top5 Hit Rate：1.0
- MRR：1.0

需要注意，这组结果来自有限的测试查询，不能直接说明系统在所有查询场景下都有同样的检索效果。

**局限与取舍：**

Recall@K 和 MRR 关注检索结果，不直接衡量 LLM 最终回答是否准确。

此外，**评测结果依赖人工标注的相关文档**。如果测试集规模太小或标注不准确，指标就缺乏代表性。

### 2. Agent 评估指标

**定义：**

Agent 评估是通过测试案例衡量 Agent 是否正确选择工具、成功执行任务并完成用户请求。

⭐常见指标：

- **工具选择准确率**（Tool Selection Accuracy）
- **任务完成率**（Completion Rate）
- **工具调用成功率**（Tool Call Success Rate）
- **引用有效率**（Citation Validity Rate）

**目的：**

判断 Agent 是否能够**正确理解用户意图**、**选择合适工**具，**并根据工具结果完成任务**。

**原理：**

假设有一组测试案例，每个案例都定义了预期行为。

例如：

```text
用户问题：
查询今天的大模型新闻。

预期：
调用新闻检索工具，返回相关结果。

实际：
调用了新闻检索工具，并成功返回结果。
```

然后根据预先定义的评估规则统计指标。

常见计算方式：

```text
工具选择准确率 = 工具选择正确的案例数 / 总案例数

任务完成率 = 成功完成任务的案例数 / 总案例数

工具调用成功率 = 成功执行的工具调用次数 / 总工具调用次数

引用有效率 = 有效引用数量 / 总引用数量
```

实际评测时，需要明确每个指标的统计口径，避免不同测试案例之间计算方式不一致。

**实践：**

AI 资讯项目当前已有 9 个 Agent 评测案例，记录结果：

| 指标 | 当前结果 |
|---|---:|
| Tool Selection Accuracy | 1.0 |
| Completion Rate | 1.0 |
| Tool Call Success Rate | 1.0 |
| Citation Validity Rate | 1.0 |

这些结果说明当前测试案例均通过，但由于样本量有限，不能据此证明 Agent 在复杂真实场景中也能达到 100% 的准确率。

**局限与取舍：**

评估结果依赖测试集设计。如果测试案例过于简单，可能无法发现多轮对话、工具异常、无结果等问题。

因此，不能只关注最终指标，还需要检查具体失败案例和工具调用过程。

### 3. 延迟、成本与工具调用失败率

**定义：**

- 延迟：系统从**接收请求到返回结果**所花费的时间。
- 成本：模型调用、Embedding 和其他外部服务产生的资源或费用。
- 工具调用失败率：失败的工具调用次数占总工具调用次数的比例。

**目的：**

评估系统是否不仅能够完成任务，还能在合理的时间和资源消耗下稳定运行。

**原理：**

延迟通常可以统计：

- 平均延迟（Average Latency）
- P50 延迟
- P95 延迟

P95 表示 95% 的请求耗时不超过该值。

工具调用失败率：

```text
工具调用失败率 = 失败调用次数 / 总调用次数
```

成本则可以根据**模型调用次数、输入输出 Token 数量及服务定价**估算。

**实践：**

AI 资讯项目现有评测记录：

- 平均延迟：24.46 秒
- P50：18.56 秒
- P95：42.86 秒

这些数据可以用来观察 Agent 的响应性能。

进一步分析时，可以将总延迟拆分为模型调用、工具执行、数据库检索等环节，定位主要耗时来源。

**局限与取舍：**

平均延迟可能掩盖少数请求的长尾问题，因此需要结合 P95 等指标分析。

成本也不能只看单次模型调用价格，还需要考虑 Agent 多轮调用、Embedding 和数据处理带来的整体消耗。

### 4. 如何设计评测集？

**定义：**

评测集是由一组具有**明确输入、预期行为和评估标准的测试案例**组成的数据集合。

**目的：**

通过固定测试案例持续验证系统功能，避免修改 Prompt、工具或流程后出现质量下降。

**原理：**

一个评测案例通常包括：

- 用户输入
- 预期工具或执行行为
- 预期结果
- 评估规则

测试集需要覆盖不同类型的场景，而不是只测试正常情况。

例如：

| 测试类型 | 测试内容 |
|---|---|
| 正常查询 | 查询指定主题新闻 |
| 日期查询 | 查询某一天的日报 |
| 无结果 | 查询不存在的主题 |
| 工具异常 | 工具超时或执行失败 |
| 多轮对话 | 根据上一轮结果继续提问 |
| 日报生成 | 不存在日报时请求生成 |

**实践：**

当前项目已有 9 个 Agent 评测案例，后续可以扩展到 30 个左右，重点增加日期查询、无结果、工具失败和多轮对话场景。

还需要检查每个案例是否有明确的预期行为，不能只看模型是否生成了看起来合理的回答。

**局限与取舍：**

评测集数量增加不代表评测质量一定提高。测试案例需要覆盖真实使用场景，并且预期结果和评价标准应尽可能明确。

### 5. 如何分析项目不足和优化方向？

**定义：**

项目优化是根据**实际测试结果**、**运行日志**和**用户需求**，定位系统问题并进行针对性改进的过程。

**目的：**

避免只增加技术组件，而是根据真实问题决定是否需要优化。

**原理：**

可以按照系统链路定位问题：

```text
数据采集
   ↓
数据清洗与去重
   ↓
Embedding
   ↓
向量检索
   ↓
Agent 工具选择
   ↓
LLM 生成回答
   ↓
结果评估
```

不同环节可能出现不同问题：

- 数据采集：新闻源不稳定、正文抽取失败。
- 数据处理：重复数据、数据缺失。
- 向量检索：相关文档没有进入 Top-K。
- Agent：工具选择错误或参数不正确。
- 生成回答：信息遗漏、事实错误或引用不准确。

应该先定位问题所在，再选择相应优化方式。

**实践：**

AI 资讯项目目前可以重点关注：

1. 扩充评测案例，提高测试覆盖度。
2. 分析 Agent 选择错误工具的情况。
3. 检查检索结果与最终回答之间的一致性。
4. 分析模型调用次数和整体响应延迟。
5. 检查新闻数据、SQLite 和 Chroma 向量数据之间的一致性。

**局限与取舍：**

优化需要结合实际问题，不应为了简历而盲目增加 Rerank、多 Agent 或其他组件。

例如，如果问题主要来自数据抽取质量，单纯优化向量检索并不能解决根本问题。

### 6. 项目介绍与技术面试

**定义：**

项目面试是围绕项目背景、系统架构、关键技术、实现细节和设计取舍展开的技术交流。

**目的：**

让面试官判断候选人是否真正理解项目，是否具备独立分析和解决问题的能力。

**原理：**

⭐项目介绍通常按照以下顺序组织：

1. 项目背景：**解决什么问题**。
2. 整体架构：**系统由哪些模块组成**。
3. 核心流程：**数据如何流转**。
4. 技术选型：**为什么使用这些技术**。
5. 难点与优化：**遇到什么问题，如何解决**。
6. 项目不足：目前还有哪些**改进空间**。

**实践：**

准备以下内容：

- 3 分钟自我介绍。
- 10 分钟 AI 资讯项目介绍。
- Python 基础问题。
- RAG 检索和生成问题。
- Agent、Tool Calling 和 LangGraph 问题。
- MCP、Prefect 和 Docker 工程化问题。

重点围绕真实代码和实际实现回答，不要将学习过但未落地的功能说成项目成果。

**局限与取舍：**

项目介绍不能只罗列技术名词。面试官更关注技术**为什么这样设计**、**具体如何实现**、**出现问题如何排查**，以及**方案有哪些不足**。

### 7. Agent 评估
按照你原来的五段式结构学习：
1. 定义：通过测试案例检查 Agent 是否正确理解问题、选择工具、传递参数并完成任务。
2. 目的：定位 Agent 执行链路中的问题，而不只是判断最终回答是否正确。
3. 原理：
   - Tool Selection Accuracy：工具选择是否正确。
   - Parameter Accuracy：工具参数是否正确。
   - Tool Call Success Rate：工具是否成功执行。
   - Task Completion Rate：是否完成用户任务。
   - Citation Validity：引用是否真实有效。
   - Recall@K、MRR：检索结果是否相关、是否排在前面。
4. 实践：结合你的 9 个 Agent 测试案例和 4 个检索查询，分析测试结果。
5. 局限与取舍：样本量较小，不能用 100% 的测试结果证明真实环境下准确率为 100%。
需要重点掌握的追问：
- Agent 最终回答错误，如何判断是工具选择、检索还是生成的问题？
- 如何设计正常查询、无结果、工具异常、多轮对话等测试案例？
- 为什么不能只看最终回答？
- 如何分析工具调用轨迹？

### 8. Agent 稳定性
1. 定义：让 Agent 执行过程可控，发生异常时能够识别、恢复或安全退出。
2. 目的：避免无限等待、无限循环、工具异常导致整个服务不可用。
3. 原理：
   
| 技术 | 作用 | 你的项目场景 |
|------|------|------------|
| 超时控制 | 避免工具一直等待 | MCP 新闻搜索 |
| 有限重试 | 应对临时网络或服务异常 | 工具调用、数据采集 |
| 最大执行步数 | 避免 Agent 无限循环 | LangGraph 执行 |
| 异常兜底 | 失败时返回明确错误 | MCP 工具调用失败 |
| 并发限制 | 控制资源使用 | 多工具并行 |
| 状态持久化 | 保存和恢复执行状态 | LangGraph Checkpointer |

1. 实践：
   - Prefect 已有任务调度和失败重试机制。
   - Agent 工具调用有超时、异常处理和兜底逻辑。
   - 后续可以补充重复工具调用检测、并发限制和运行监控。
2. 局限与取舍：
   - 重试不是越多越好。
   - 参数错误、权限错误不应该盲目重试。
   - 超时后需要考虑任务取消。
   - 并行执行可以降低等待时间，但会增加资源消耗。
需要重点掌握的追问：
- 工具超时后 Agent 应该怎么办？
- 哪些错误适合重试，哪些不适合？
- 如何避免 Agent 无限调用工具？
- 多个工具什么时候适合并行？
- Checkpointer 能解决什么问题，不能解决什么问题？

## 三、学习复盘

**今天还没搞懂的内容：**

- 当前评测集只有少量测试案例，如何判断评测结果是否具有代表性？
   少量测试案例只能说明系统在当前测试样本上的表现，不能直接代表整体能力。
   我会从三个方面判断：
   1. 测试覆盖度： 是否覆盖正常查询、无结果、时间过滤、工具调用失败、多轮对话等不同场景。
   2. 样本多样性： 是否包含不同主题、不同表达方式、不同时间范围和不同难度的问题，避免测试案例过于相似。
   3. 结果稳定性： 对于存在模型随机性的任务，可以重复运行多次，观察工具选择和回答质量是否稳定。
   后续我会逐步扩大测试集，例如从当前少量案例扩展到 30～50 个，再根据实际错误类型持续补充。
   同时保留固定的回归测试集，每次修改 Prompt、检索策略或工具描述后重新评测，比较指标变化。

- 检索结果正确，但最终回答错误时，应该如何定位问题？
如果检索结果正确，但最终回答错误，我会先区分**检索问题和生成问题**。
首先检查传给 LLM 的**上下文是否完整**，是否存在截断、关键信息遗漏或者上下文排序问题。
然后检查 **Prompt 是否明确要求模型基于检索结果回**答，是否存在指令冲突。
接着检查模型**是否正确理解了上下文**，有没有出现信息误读、推理错误或者根据自身知识补充了不存在的信息。
最后检查引用**是否和实际回答对应**，避免出现引用了正确新闻，但回答内容却没有得到新闻支持的情况。
定位时，我会保留同一次请求的检索结果、Prompt、模型输入输出和引用信息，逐步确定错误发生在哪个环节。

| 排查位置   | 可能问题                          | 改进方式                                  |
| ---------- | --------------------------------- | ----------------------------------------- |
| 上下文构建 | 检索正确，但传给 LLM 的内容不完整 | 检查上下文拼接、截断和排序                |
| Prompt     | 没有限制模型只能依据检索内容回答  | 明确回答依据和无答案处理规则              |
| LLM 生成   | 误解内容、推理错误、产生幻觉      | 优化 Prompt，增加事实核验                 |
| 引用校验   | 引用存在，但不能支持回答          | 校验新闻 ID、引用内容和回答之间的对应关系 |

**记住一个关键点：检索正确不等于回答正确。** RAG 需要分别评估检索质量和生成质量。

**需要面试前回顾的内容：**

- Agent 的工具选择准确率、任务完成率、工具调用成功率和引用有效率分别衡量什么？
  会把 Agent 的评测拆成不同环节。工具选择准确率衡量决策是否正确，工具调用成功率衡量工具执行是否正常，任务完成率衡量最终是否满足用户需求，引用有效率衡量回答中的引用是否真实且能够支撑结论。这样可以区分问题到底出在 Agent 决策、工具执行，还是最终回答质量上。

| 指标           | 衡量什么                     | 举例                                                   |
| -------------- | ---------------------------- | ------------------------------------------------------ |
| 工具选择准确率 | Agent 有没有选对工具         | 用户问新闻内容，是否选择 `search_news`，而不是日报工具 |
| 任务完成率     | Agent 最终有没有完成用户目标 | 用户要求查询某主题新闻，是否给出符合要求的结果         |
| 工具调用成功率 | 工具本身有没有正常执行       | MCP 工具是否正常返回结果，而不是超时或报错             |
| 引用有效率     | 回答中的引用是否真实、有效   | 回答引用的新闻 ID 是否存在，引用内容是否支持对应结论   |
- RAG 的 Recall@K、MRR 等指标有什么区别？
  Recall@K 衡量前 K 条结果覆盖了多少相关文档，主要看检索是否查全；MRR 衡量第一个相关结果的排名，主要看相关结果是否排在前面。我的项目可以通过 Recall@5 和 MRR 评估新闻检索效果。不过需要先准备人工标注的相关文档集合，才能计算这些指标，不能仅凭检索结果数量判断检索质量。

- 如何设计测试案例，覆盖正常查询、无结果、工具失败和多轮对话？
   我会先根据 Agent 的使用场景划分测试类型，再为每类设计输入、预期行为和评价标准。
   正常查询主要检查**工具选择和结果准确性**；无结果场景检查系统是否明确告知没有检索到内容，而不是编造；工具失败场景检查超时、异常和重试兜底；多轮对话则检查是否能正确理解上下文和追问。
   每个案例都记录测试输入、预期工具、预期结果、实际结果和是否通过，形成固定的回归测试集。

- 如何结合评测结果定位并改进系统问题？
  **核心思路：先看哪个指标异常，再定位对应环节，最后针对性修改并重新评测。**

| 评测现象         | 可能问题                          | 改进方向                                |
| ---------------- | --------------------------------- | --------------------------------------- |
| 工具选择准确率低 | 工具描述不清楚、Prompt 有歧义     | 优化工具描述、参数 Schema 和系统提示词  |
| 工具调用成功率低 | API 异常、超时、参数错误          | 检查工具实现、超时、重试和参数校验      |
| 任务完成率低     | 多环节配合失败                    | 根据执行日志检查完整链路                |
| Recall@5 低      | 相关文档没有被召回                | 优化切分、Embedding、混合检索和过滤条件 |
| MRR 低           | 相关文档排名靠后                  | 优化排序策略，引入 Reranker             |
| 引用有效率低     | 引用 ID 错误或引用与回答不匹配    | 增加引用校验和回答依据检查              |
| 回答准确性低     | 上下文不足、Prompt 或模型生成问题 | 检查上下文、Prompt 和模型输出           |

### **面试回答**

> 我会先根据评测指标定位问题所在的模块，而不是直接修改模型。
>
> 例如，工具选择准确率低，就检查工具描述和 Prompt；Recall@5 低，就检查 Embedding、检索条件和数据质量；如果检索结果正确但回答准确性低，就进一步检查上下文构建和 LLM 生成。
>
> 修改后重新运行固定评测集，对比修改前后的指标。如果目标指标提升，同时其他指标没有明显下降，就保留这次优化；如果出现回归，就继续分析原因。
