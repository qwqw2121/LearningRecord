### 1. 项目完整数据流：RSS → 清洗 → 抽取 → 分析 → 去重 → Embedding → Chroma → RAG → Agent → MCP

**定义：**

这是一个 AI 资讯智能处理系统，通过自动采集新闻、处理数据、构建知识库，再利用 RAG 和 Agent 实现新闻检索与问答。

**目的：**

解决人工收集 AI 资讯效率低、新闻数量多、信息分散、难以快速检索和总结的问题。

**原理：**

整体分为三个阶段：

1. 数据处理阶段：RSS 采集新闻，进行清洗、正文抽取、LLM 分析和去重。
2. 知识库构建阶段：将新闻文本转换为 Embedding 向量，存入 Chroma，支持语义检索。
3. 智能问答阶段：用户提出问题，Agent 根据问题选择工具，通过 MCP 调用新闻检索等功能，结合 RAG 检索结果生成回答。

**实践：**

项目主要流程：

- RSS：从多个资讯源采集新闻。
- 清洗与抽取：清理原始数据，提取新闻正文。
- 分析：调用 LLM 生成摘要、分类、关键词和重要性等信息。
- 去重：识别重复新闻，避免重复入库。
- Embedding：调用 DashScope `text-embedding-v3` 生成文本向量。
- Chroma：存储向量，支持语义检索。
- RAG：检索相关新闻，为模型提供上下文。
- Agent：通过 LangGraph 单 Agent + Tool Calling 决定调用哪些工具。
- MCP：将新闻检索、日报查询等能力封装为工具，供 Agent 调用。

**局限与取舍：**

- RSS 依赖资讯源，可能存在采集失败、内容不完整的问题。
- LLM 分析存在不稳定性，需要进行结果校验。
- Embedding 和向量检索不能保证每次都找到最相关的内容。
- Agent 增加了灵活性，但也会增加调用延迟和模型成本。

当前采用确定性数据处理流程与 LLM 智能分析相结合的方式，避免把所有任务都交给 Agent。

### 2. Prefect 和 LangGraph 分别解决什么问题？

**定义：**

- Prefect：**Python 工作流编排与调度框架**，负责管理任务执行。
- LangGraph：基于图结构的 **Agent 工作流框架**，负责管理模型、工具和状态之间的交互。

**目的：**

Prefect 主要解决定时执行、任务依赖、失败重试等**工程问题**。

LangGraph 主要解决 Agent 执行过程中**状态传递、条件路由和工具调用**等问题。

**原理：**

Prefect：

- Flow 表示一个完整工作流。
- Task 表示工作流中的具体任务。
- 通过任务调用关系组织执行顺序。
- 支持重试、日志和调度。

LangGraph：

- State：保存工作流运行状态。
- Node：执行具体逻辑。
- Edge：决定节点之间的执行关系。
- 条件路由：根据当前状态决定下一步执行哪个节点。

**实践：**

项目中：

- Prefect 负责 RSS 采集、清洗、抽取、分析、去重和向量化等数据处理任务。
- LangGraph 负责用户提问后的 Agent 处理，通过 Tool Calling 选择新闻检索、日报查询等工具。

两者分别负责数据处理层和智能交互层。

**局限与取舍：**

- Prefect 不适合替代 Agent 的动态决策逻辑。
- LangGraph 不适合替代成熟的数据调度和 ETL 管理工具。
- 同时使用两个框架会增加一定的学习和维护成本。

因此，项目将确定性较强的数据处理交给 Prefect，将需要模型决策和工具调用的任务交给 LangGraph。

### 3. SQLite 和 Chroma 为什么同时使用？

**定义：**

- SQLite：关系型数据库，用于存储结构化数据。
- Chroma：向量数据库，用于存储 Embedding 并进行向量相似度检索。

**目的：**

新闻数据既需要按照日期、分类、状态等条件进行精确查询，也需要根据语义相似度查找相关内容。

单独使用其中一种数据库不能很好地满足两类需求。

**原理：**

SQLite：

- 通过表、行、列组织结构化数据。
- 使用 SQL 完成数据增删改查。
- 支持索引和事务。

Chroma：

- 保存文本对应的向量及相关元数据。
- 将查询文本转换为向量。
- 根据向量距离计算相似度，返回 Top-K 相关结果。

**实践：**

- SQLite 的 `news.db` 保存新闻原始信息、摘要、分类、关键词、处理状态和日报等数据。
- Chroma 保存新闻对应的 Embedding，用于语义检索。
- 用户可以通过 SQLite 查询**指定日期或分类**的新闻，也可以通过 Chroma 查找**语义相关**的新闻。

**局限与取舍：**

- SQLite 不擅长直接进行大规模语义向量检索。
- Chroma 不适合替代关系型数据库承担复杂业务数据管理。
- 两个存储系统需要维护数据关联和一致性。

当前项目规模较小，SQLite 部署简单，Chroma 可以直接支持向量检索，因此采用两者结合的方案。

### 4. 项目中哪些是确定性流程，哪些需要 LLM 参与？

**定义：**

- 确定性流程：输入和执行逻辑明确，相同条件下通常能够得到可预期的结果。
- LLM 智能处理：利用大模型进行文本理解、分析、生成和决策，结果具有一定不确定性。

**目的：**

明确不同任务适合使用什么技术，避免所有环节都依赖大模型，降低成本和系统的不稳定性。

**原理：**

确定性流程主要依赖**程序逻辑和规则**执行，例如数据清洗、数据库操作、状态更新。

LLM 处理主要依赖**模型推理**，例如新闻摘要、分类、关键词提取和 Agent 工具选择。

**实践：**

确定性流程：

- RSS 数据采集与解析。
- 数据清洗和正文抽取。
- 规则去重和数据库操作。
- Embedding API 调用及向量入库。
- Prefect 任务调度与重试。

LLM 参与：

- 新闻摘要生成。
- 新闻分类和关键词分析。
- 用户问题理解。
- Agent 工具选择。
- 基于检索上下文生成回答。

**局限与取舍：**

- 纯规则方式稳定，但难以处理复杂语义。
- LLM 理解能力强，但存在结果不稳定、响应延迟和调用成本。
- 因此采用混合架构：能用代码明确完成的任务尽量使用代码，需要语义理解和生成的任务交给 LLM。

## 三、学习复盘

**今天还没搞懂的内容：**

- Prefect 的 Flow 和 Task 具体如何组织执行。 
 task存放具体的工作任务，flow根据任务顺序编排并同时更新state同步
prefect 中，Task 负责**封装具体的业务操作**，Flow 负责组织和编排 Task，定义**执行顺序、依赖关系和异常处理**。Prefect 会自动跟踪 Flow 和 Task 的运行状态，例如 Running、Completed 和 Failed，并支持失败重试、定时调度等能力。
各个 Task 之间传递的是同一个业务状态对象 PipelineState，代表一次 Pipeline 运行过程中的上下文信息。同一个对象被修改后继续传递

我的项目中有三层状态管理。Prefect 自身负责跟踪 Flow 和 Task 的运行状态；我通过 Pydantic 定义了 PipelineState，用来**保存一次流水线运行的日期、成本控制参数和阶段统计信息**；
 *另外，数据库中的 NewsStatus 用于跟踪每条新闻的业务处理进度，例如正文提取、LLM 分析、向量化和事件聚类状态。*  有但是prefect/state里的没用到，只是列举

**- LangGraph 中 State 如何在 Node 之间传递。**：
核心理解：State 是整个 Graph 共享的状态对象，Node 读取当前 State，执行任务后返回状态更新，使用**MessagesState**：预置的消息状态，messages 字段自动追加，适合对话/Agent  
LangGraph **通过 State 在不同 Node 之间共享上下文**。每个 Node 接收当前 State，执行相应逻辑后返回需要更新的字段，Graph 根据字段对应的 Reducer 合并状态，再将更新后的 State 传递给下一个 Node。
在我的项目中，Agent 使用 messages 保存用户消息、模型回复和工具调用结果，因此模型能够根据之前的对话和工具返回结果继续决策。

- SQLite 和 Chroma 中的数据如何关联，如何保证一致性。 ： 
news_id。
我的项目使用 SQLite 存储新闻的结构化业务数据，使用 Chroma 存储新闻的 Embedding 向量。两者通过 news_id 关联。
用户进行语义检索时，先从 Chroma 获取匹配的新闻 ID，再回到 SQLite 查询完整新闻内容。
由于 SQLite 和 Chroma 是独立存储，无法使用一个事务保证两边原子提交，因此我通过处理状态管理、失败重试、幂等写入和后续数据校验来保证最终一致性。

采用的是 LangGraph 单 Agent + Tool Calling + MCP 工具架构。

从用户提问到 Agent 返回答案，可以分成六个阶段：
1. 用户请求进入 FastAPI 后端。
2. 后端调用 LangGraph Graph。
3. Agent Node 将用户问题和历史消息交给 LLM。
4. LLM 判断是否需要调用工具。
5. Tool Node 执行对应 MCP 工具，并将结果返回给 Agent。
6. Agent 根据工具结果生成最终答案，返回前端
